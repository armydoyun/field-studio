# Shader Art 추가 로직·효율 분석 및 수정 · 2026-10-15 · 2차

## 기준과 결론

직전 1차 수정본 a.zip을 기준으로 분석했다. 핵심 GPU 프로그램의 준비 후 교체 구조는 유지하고, 비동기 입력의 시점 일관성, 캡처/재생 상태, 복구 실패, 저장 순서, 편집기의 반복 처리를 수정했다.

실행 모듈 추가 없음. 외부 런타임 의존성 추가 없음. JS 전체 169,328 → 171,928바이트(+2,600, 약 1.54% 증가). 안전한 취소와 복구 처리를 추가하면서, 기존 반복 작업과 중복 검증을 제거했다. 파일 크기 감소를 성능 개선의 근거로 사용하지 않았다.

## 실제 오류: 비동기 파일 입력이 현재 작업을 덮어쓰는 문제

### 원인
- Pack의 file.text(), 이미지 디코딩, IndexedDB 저장이 끝날 때까지 사용자는 계속 편집·탭 전환·다른 가져오기를 할 수 있다.
- 이전 구현은 완료된 시점의 편집 대상과 설정을 사용했다. 늦게 끝난 이전 가져오기가 새 작업을 덮어쓸 수 있었다.
- GLSL 파일도 읽기 시작한 탭이 아니라 완료 시 선택된 탭에 들어갔다.

### 수정
studio.js의 beginLoad가 요청 번호, 편집 프로젝트, 선택 탭을 기록한다. Pack은 적용된 GPU 프로젝트와 설정도 기록한다. await 이후 기록과 현재 상태를 확인하고 작업이 바뀌었으면 명시적으로 취소한다. 더 나중에 시작한 파일 요청은 이전 요청을 무효화한다.

이미지 단독 추가는 파일 자체를 라이브러리에 남기되 작업 변경 후 자동 채널 연결을 취소한다. Pack 가져오기에서 실패하면 이미 추가된 임시 이미지들을 정리한다. 컨텍스트 손실 중에도 CPU 이미지 삭제와 채널 해제는 가능하게 했다.

가져오기 실패 후 설정 롤백이 필요한 경우에는 마지막 GPU 소스뿐 아니라 가져오기 전의 미적용 편집본과 dirty 상태도 되돌린다. 종료된 Studio의 setProject도 차단한다.

## 실제 오류: 캡처의 임시 재생 상태

### 원인
일시정지 중 캡처는 한 프레임만 그리기 위해 running=true, capturePaused=true를 사용한다. 탭 숨김/컨텍스트 손실 때 capturePaused만 지우면 running=true가 남아, 복귀 후 계속 재생된다. 반대로 사용자가 직접 Play를 눌러도 남아 있는 capturePaused가 다음 프레임에서 재생을 멈췄다.

### 수정
숨김/손실 때 임시 캡처용 재생이면 running도 false로 복원한다. 명시적인 start는 capturePaused를 해제해 사용자의 Play 의도를 우선한다. 기존 stop과 캡처 Promise 취소 계약은 유지한다.

## 실제 오류: FPS 제한의 누적 지연

### 원인
다음 프레임 시점을 항상 now+interval 이상으로 밀었다. 144Hz에서 60FPS의 16.67ms 간격을 만족하는 첫 rAF는 약 20.83ms이므로, 매번 늦은 시점에서 다시 예약하면 약 48FPS가 된다.

### 수정
기존 예약 시점에서 일정한 간격으로 전진하고 놓친 구간만 건너뛴다. 늦은 프레임마다 시간 기준을 다시 잡지 않는다. 긴 중단 뒤 밀린 프레임을 한꺼번에 그리는 루프도 만들지 않았다.

검증은 144Hz 간격의 모의 rAF 10초분이다. 수정 전 480프레임, 수정 후 약 600프레임을 검사했다. 실제 GPU 성능 측정은 아니다.

## 실제 오류: 컨텍스트 복구 실패 후 부분 자원과 재시도

### 원인
Image 재생성 후 Buffer 복구가 실패하면 새 Image 프로그램/VAO가 남았다. 애플리케이션의 lost 상태만 true가 되어 이후 start가 아무 프레임도 예약하지 못했다.

### 수정
복구 중 새로 만들어진 Image/VAO 및 부분 GPU 자원을 정리한다. PassManager와 TextureInput의 onLost(release=true)는 살아 있는 새 컨텍스트의 부분 자원을 해제하는 경로다. 실제 contextlost 이벤트는 release=false로 호출하여 무효한 이전 핸들을 삭제하지 않는다.

실제 GL 컨텍스트가 살아 있다면 Play가 복구를 다시 시도한다. 복구가 실패한 상태에서 프레임을 실행하지 않는다. CPU 이미지 원본과 패스 정의는 재시도를 위해 보존한다.

## 실제 오류: 이미지 저장과 삭제 순서

### 원인
각 쓰기가 독립적으로 IndexedDB를 열었다. 먼저 요청한 저장보다 나중 요청한 삭제가 먼저 완료되면, 늦은 저장이 삭제한 레코드를 다시 만들 수 있었다. 메모리/GPU에서는 삭제됐는데 새로고침 후 이미지가 되살아나는 형태다.

### 수정
TextureInput 내부의 짧은 Promise 큐가 저장·샘플링 변경·삭제를 요청 순서대로 실행한다. 한 작업의 저장 실패가 뒤 작업을 막지 않도록 큐의 오류를 분리한다. 이미지 디코딩과 GPU 업로드 자체를 저장 큐에 넣지는 않는다.

Pack은 샘플링 옵션을 최초 addTexture에 전달한다. 기존의 추가 저장 → 샘플링 변경 → 재저장을 한 번의 저장으로 줄였다. base64 디코딩 결과는 크기를 정한 Uint8Array에 직접 채워 임시 문자열 순회 목록을 피한다. 바이트 값 0/255/128 보존을 검사했다.

## 실제 오류: 검색과 치환의 Unicode 위치

### 원인
소스 전체를 소문자로 바꾼 문자열에서 찾은 위치를 원본에 적용했다. 대소문자 변환으로 길이가 바뀌는 문자가 앞에 있으면 위치가 어긋난다. 예를 들어 주석의 İ 앞뒤에서 foo 검색이 oo를 선택하거나, 전체 치환이 다른 글자를 지웠다.

### 수정
검색어의 정규식 문자를 이스케이프한 뒤 원문에서 대소문자 무시 검색을 수행한다. 검색과 치환은 같은 위치 계산을 공유한다. 교체 문자열의 $&/$1도 일반 텍스트로 넣는다. 전체 치환은 원문 조각과 교체 문자열을 모아 한 번에 합친다. 매 일치마다 전체 소스를 소문자로 바꾸거나 전체 결과를 다시 복사하지 않는다.

## 실제 오류: IME 조합 중 편집 단축키

textarea의 keydown 진입점에서 isComposing을 확인한다. 조합 중 Tab이 들여쓰기를 실행하거나 Ctrl+Z가 Studio 이력을 이동하던 경로를 막았다. 개별 분기에 중복돼 있던 조합 검사는 제거했다. 입력 이벤트 자체는 계속 처리한다.

## 실제 오류: 저장 설정의 일괄 복원·초기화와 검증

### 원인
- 사용자 Uniform 64개를 순차 등록하면서 프로그램을 64회 다시 빌드했다.
- 초기화도 하나씩 제거했으므로 뒤쪽 제거에서 컴파일이 실패하면 앞의 일부만 사라졌다.
- Pack 필수 int 검증은 정수 여부만 확인하여 int32 범위 밖의 값도 통과시켰다. 실제 setUniform에서 뒤늦게 실패하면 앞서 FPS 등의 설정이 이미 바뀌었다.

### 수정
Renderer.setUserUniforms가 목록을 검증하고 기존 준비 후 교체 경로로 한 번에 바꾼다. Settings는 정상 저장 목록을 일괄 복원하고, 잘못된 항목이 있는 구형 데이터에는 항목별 복원의 기존 동작을 사용한다. 초기화는 전체 목록 제거가 성공한 뒤 다른 설정을 바꾼다. Uniform이 없으면 불필요한 재컴파일을 하지 않는다.

필수 Uniform 값의 사전 검증도 Renderer.validateUniformValue(기존 normalizeUniform)를 사용한다. 등록 경로와 Pack 경로가 동일한 값 규칙을 공유한다.

## 실제 오류: 자신이 내보낸 파일을 다시 열지 못하는 제한

- 기존 프로젝트 JSON의 가져오기 제한은 2MiB지만 Image+Buffer 8개의 정상 소스 길이 합계는 이를 넘을 수 있었다. JSON 가져오기/내보내기 예산을 16MiB로 맞췄다.
- 이미지 32MiB의 base64와 여러 소스의 JSON 이스케이프/UTF-8 크기를 고려해 Pack 가져오기/내보내기 예산을 64MiB로 맞췄다. 이미지별 12MiB, 이미지 합계 32MiB, 패스 수와 소스 길이 제한은 유지한다.
- GLSL의 소스 길이와 UTF-8 파일 바이트 수는 다르다. 파일 읽기 예산은 1MiB, 디코딩된 소스는 262144자 이하로 확인한다. 한글 주석이 많은 유효 길이의 소스를 다시 읽을 수 있다.
- 내보내기도 대응 파일 예산을 검사하므로 과도한 메타데이터로 가져오기 예산을 넘는 파일을 조용히 생성하지 않는다. 원시 .frag 내보내기는 편집본 백업 기능을 유지한다.

프로젝트 JSON은 실제 2MiB 초과 파일을 내보내고 다시 가져오는 왕복 검사로 확인했다. Pack 49MiB 경계는 모의 파일의 size/text 경계를 이용한 정책 검사이며 49MiB의 실제 이미지 GPU 업로드 검사가 아니다. 소스 길이/형식 자체가 유효하지 않은 미적용 편집본까지 실행 가능한 프로젝트가 된다는 의미는 아니다.

Undo 스냅샷은 JSON 왕복 대신 작은 객체/배열만 복사하고 소스 문자열은 그대로 참조한다. 불변 문자열이라 이전 이력의 내용이 이후 편집으로 바뀌지 않는다. 구조 비교도 JSON 생성 없이 필드와 문자열을 직접 비교한다. Undo/Redo 결과와 외부로 반환한 스냅샷의 독립성을 검사했다. 자동 저장 시점의 실제 JSON 직렬화는 필요하므로 유지한다.

하이라이트와 함수 탐색은 소스 문자열을 기준으로 마지막 결과를 보관한다. 함수 탐색과 자동 완성은 분석 결과를 공유한다. 소스 변경 시 캐시가 갱신되는 검사도 포함한다. 가상 스크롤/별도 문서 모델/새 파서 계층은 추가하지 않았다.

## 검증과 한계

- deep-regression: 34개 통과. 직전 1차 실행 소스에 같은 검사를 실행하면 6개 통과/28개 실패. 이는 테스트 시나리오 수이며 서로 독립적인 버그 수가 아니다.
- logic-regression: 기존 19개 통과.
- architecture-regression: 기존 44개 통과.
- 이미지/샘플링/설정/모달/기본 예제/Starter/코드접기 롤백/UI 정적 검사 통과.
- 실행 JS 문법, 수정 테스트 문법, AMD 인자/의존성/DOM 연결, SHA-256 무결성을 최종 확인한다.
- 실제 브라우저·GPU·IndexedDB 엔진을 실행한 결과는 아니다. DOM/WebGL/DB 비동기 경계를 모의한 회귀 검사다. 실제 장치별 컨텍스트 손실·복구 및 GLSL 드라이버 컴파일은 별도 확인이 필요하다.
- 기존 자동 Uniform 선언 인식은 완전한 GLSL 전처리기/파서가 아니다. 복잡한 #if/매크로 조합까지 동작을 보장한 것으로 해석하면 안 된다.
